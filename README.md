# QA Testbed（2D）— 自動プレイテスト比較用の小さなゲーム

バグを8個仕込んだ2Dグリッドゲームと、それを探索するエージェント（ランダム／Go-Explore）、
人間のテストプレイを記録する仕組み、結果を集計・グラフ化するスクリプトのセットです。

- ゲームのルールは **UnityEngine に依存しない純粋な C#**（`Assets/QaTestbed/Core`）で書いてあります。
  そのため、状態の丸ごと保存・復元（Go-Explore の「戻る」）ができ、乱数シードが同じなら結果も毎回同じです。
- Unity 側（`Assets/QaTestbed/Unity`）は「表示」「人間の操作」「実験の実行ボタン」だけを担当します。
- 素材（画像など）は不要です。スプライトはコードで生成します。

## フォルダ構成

```
Assets/QaTestbed/
  Core/                 ゲーム本体・バグ・自動判定・エージェント・実験・人間の記録（純粋な C#）
  Unity/                GridGameView（遊ぶ・観る）, ExperimentRunnerBehaviour（実験）, QaPaths
analysis/plot_curves.py 結果のグラフ化・集計（Python）
Tools/QaConsole/        Unity を開かずに実験・検証を回すコンソール版（任意、.NET 8）
sample_results/         こちらで回した予備実験の結果（参考）
```

## セットアップ（5分）

1. Unity Hub で新規プロジェクトを作る（Unity 2022.3 LTS 以降 / Unity 6。テンプレートは「2D」系ならどれでも可）
2. このフォルダの `Assets/QaTestbed` を、プロジェクトの `Assets/` の下にコピーする
   - `Tools/` と `analysis/` は Assets の中に入れないでください（Unity がコンパイルしようとしてエラーになります）
3. シーンに空の GameObject を作り、`GridGameView` を追加して Play
   - 盤面が表示され、矢印キー（WASD）で動かせれば成功です

## 使い方

### 1. 人間がテストプレイする（人間の比較実験）

`GridGameView` の Inspector で:

| 項目 | 設定 |
|---|---|
| mode | `HumanPlay` |
| participantId | 参加者ID（例 `P01`） |
| skillLevel | スキルの区分（例 `beginner` / `gamer` / `developer`） |
| timeLimitSeconds | 制限時間（例 600 = 10分） |
| enableAllBugs / randomSubset | どのバグを有効にするか |

操作: 矢印/WASD 移動、Space/E 調べる、**B バグ報告**、R やり直し、Esc 終了して保存

- 参加者には「バグだと思ったら B を押して、何が起きたかをメモする」とだけ伝えます（バグの一覧は見せない）
- 記録は `QaResults/human_<ID>_<日時>.csv` に保存されます。列 `event` の意味:
  - `trigger` … バグのコードが実行された（＝バグを**起こした**）※本人には見えない
  - `oracle` … 自動判定が異常を検出した ※本人には見えない
  - `report` … 本人が B を押した（＝バグに**気づいた**）。何に気づいたかはメモと突き合わせる
  - `restart` / `clear` / `finish`
- これで「起こしたのに気づかなかった」「気づくまでに何秒かかった」が人間についても測れます

### 2. エージェントの探索を観る

`mode = WatchAgent`、`agentKind` に次のどれかを入力して Play:
`Random` / `GoExplore(Position)` / `GoExplore(Position+Keys)` / `GoExplore(Full)`

Go-Explore では、プレイヤーが離れた場所に瞬間移動するように見えます。これがアーカイブからの「戻る」（スナップショット復元）です。
訪れた床は青っぽく表示されます。

### 3. 比較実験を回す

空の GameObject に `ExperimentRunnerBehaviour` を追加 → Inspector でコンポーネント名を右クリック →「Run Experiments」。
（既定: 4手法 × 10シード × 20,000ステップ。数秒で終わります）

結果はプロジェクト直下の `QaResults/<日時>/` に出力されます。

Unity を開かずに回す場合（任意、.NET 8 SDK が必要）:

```
cd Tools/QaConsole
dotnet run -c Release -- run --budget 20000 --seeds 10 --mode all --out ../../QaResults
dotnet run -c Release -- verify     # 誤検出がないこと・全バグが検出可能なことの確認
```

`--mode` は `all`（全バグ有効）/ `single`（1個ずつ）/ `subset`（`--subset 4` 個をランダムに）。

### 4. グラフと集計

```
pip install pandas matplotlib
python analysis/plot_curves.py QaResults/<日時>
```

| 出力 | 内容 |
|---|---|
| `fig_detection_curve.png` | 予算（ステップ数）ごとの検出率。線＝平均、帯＝シード間の最小〜最大 |
| `fig_coverage_curve.png` | 予算ごとの網羅率 |
| `fig_coverage_vs_detection.png` | 最終網羅率と検出率の関係（1点＝1回の実行） |
| `fig_bug_matrix.png` | バグ×手法の「起こした率」と「気づいた率」 |
| `summary_agents.csv` | 手法ごとの面積（AUC、0〜1）と予算別の検出率 |
| `summary_bugs.csv` | バグごとの起こした率・気づいた率・検出までの中央値ステップ |

面積（AUC）＝ 検出率の曲線の下の面積 ÷ 予算。早く見つけるほど大きくなります。

`S` スタート / `E` ゴール（Space で調べるとクリア）/ `r g b` 鍵 / `R G B` 扉（同じ色の鍵で開く。鍵は消費）/ `c` コイン /

## 仕込んだバグ

| ID | 種類 | 内容 | 起こし方 | 自動判定 | 最短手数 |
|---|---|---|---|---|---|
| R1 | 到達系 | 外壁の穴 | 大広間の西の外壁（`1`）に当たり判定がない | 到達不能なはずの位置にいる | 14 |
| R2 | 到達系 | 条件付きの壁抜け | 鍵を2本以上持って、赤い鍵の部屋の東の壁（`2`）に体当たり | 到達不能なはずの位置にいる | 36 |
| S1 | 状態系 | 鍵なしで赤い扉が開く | コインを持って、鍵なしで赤い扉に体当たり | 鍵を持たずに扉が開いた | 21 |
| S2 | 状態系 | 緑の鍵の増殖 | 部屋の出口（`3`）を踏むと緑の鍵が復活し、もう一度拾える | 同じ鍵を2回拾った | 7 |
| C1 | クラッシュ | コイン0枚でゴールすると落ちる | コインを1枚も取らずにゴールで調べる | 例外（NullReference） | 49 |
| C2 | クラッシュ | 4枚目のコインで落ちる | コインを4枚集める | 例外（IndexOutOfRange） | 30 |
| H1 | ハマり | 青い部屋への閉じ込め | 青い扉の奥に入ると背後で扉が閉まる | ゴールに到達できない状態 | 17 |
| H2 | ハマり | 動けなくなる床 | 大広間の特定の床（`4`）を踏むと移動できない | ゴールに到達できない状態 | 17 |

最短手数は `verify` で求めた「そのバグだけ有効にしたとき、検出までに必要な最短の手数」です。

自動判定（オラクル）は、どのバグが仕込まれているかを見ずに、ゲームの仕様だけで異常を検出します。
検出結果をバグIDに対応づける（採点する）処理だけが `BugCatalog.Classify` にあります。

## 設計メモ（発表で聞かれそうな点）

- **網羅率** ＝ バグを全部無効にしたときに到達できる床（133マス）のうち、訪れた割合。前回の論文の「ナビメッシュ網羅率」に相当。
- **戻る** ＝ スナップショット復元。復元自体には予算（ステップ）を消費しない（Go-Explore 論文と同じ前提）。
- **ハマり判定** ＝ 今の状態から、実際の遷移関数で幅優先探索してゴールに行けるかを調べる（`SoftlockChecker`）。
  25手ごとに実行（人間のプレイでは10手ごと）。結果は状態ごとにキャッシュするので高速。
- **Go-Explore のセルの粒度**（先生の「何を保存するかの取捨選択」に対応）:
  - `Position` … 位置のみ
  - `Position+Keys` … 位置＋持っている鍵＋開いた扉
  - `Full` … さらに床の鍵の有無・コイン枚数・凍結状態
- 戻る先の選び方は「選ばれた回数・見られた回数が少ないセルほど選ばれやすい」（元の Go-Explore の訪問回数ルール）。

## 次の段階（LLM を入れる場所）

`Core/Agents.cs` の `GoExploreAgent` の次の2か所を差し替えると、IGE と同じ構成になります。

- `SelectCell()` … どこに戻るかを LLM に選ばせる（L2）
- `Tick()` 内の行動選択 … どう動くかを LLM に選ばせる（L3）

状態をテキストにする関数（例:「位置(5,8)、緑の鍵を所持、赤い扉は閉、コイン2枚」）を用意すれば、そのままプロンプトに使えます。

## メモ
`Go-Explore`の3種類の違い

3つとも `Go-Explore`の仕組みは同じで、「何を新しい状態として保存するか」だけが違う。前資料で説明した所謂「保存のつまみ」の話にあたる。

共通の動き

選ぶ：アーカイブ（保存済みの地点）から1つ選ぶ。選ばれた回数や通りかかった回数が少ない地点ほど選ばれやすい
戻る：その地点の状態をまるごと復元する（スナップショット）
探索する：そこからランダムに30手動く（半分の確率で直前と同じ方向を繰り返す）
保存する：1手ごとに状態を「セル」の名前に変換する。初めて見るセルなら、そのときの状態を保存する

違うのは「セルの名前の付け方」だけになる。

| 手法 | セルの名前に含めるもの |
| Position | 位置 (x, y) だけ |
| Position+Keys	| 位置 ＋ 持っている鍵 ＋ 開いた扉 |
| Full | 上に加えて、床に残っている鍵・コインの枚数・動けない状態か |
